## Summary

The research says **go**. Pol.is can host NTARI's deliberations with pseudonymous, eligibility-checked voting. But it needs more protection around it than PLAN.md assumed, mostly on NTARI's own server, with no changes to Pol.is itself.

Plain-language glossary:
- **xid:** the pseudonym a member votes under. It is different in every round.
- **Proxy:** the program at the front door of NTARI's server. It decides which web addresses outsiders can reach.
- **Roll:** the list of members eligible to take part in a round.
- **Round key:** the secret that turns a Slack account into that round's xid. Destroying it at close means nobody can ever link votes back to people.

## 0. Disclosure of the Pol.is weakness (resolved)

- **What R3 found:** in the xid setup, any member who had joined a round could cast or change votes as any other member who had joined. It worked by fetching the conversation's UUID with an ordinary participant login, then downloading the list of every member's xid.
- **Who decided:** Calvin Secrest chose a private report to the Pol.is maintainers first (2026-10-12).
- **The upstream fix:** the maintainers fixed it on 2026-10-13 in [compdemocracy/polis#3048](https://github.com/compdemocracy/polis/pull/3048), now on `stable`. Only owners and moderators can get a conversation's UUID, and every existing UUID was cleared.
- **Retest:** confirmed on `d3d38cec`; the attack as R3 ran it is closed (R3 addendum).
- **Still open upstream** (smaller; NTARI's preconditions in §15 cover all of them):
  - Pol.is still identifies a voter by the xid alone, so anyone who *learns* someone's xid can vote as them;
  - the xid list download still needs no login for anyone holding an owner's link;
  - the shared-browser merge;
  - an email is still stored when email subscriptions are off.
- **Decide:** report these as ordinary public issues on the Pol.is repo (recommended now that the serious one is fixed), or in a private note to admin@compdemocracy.org.

## 1. Pol.is version and voting screen

- **Recommend:** pin `stable` at `d3d38cec8bf81ec2c67fc870ed2abacc59ad0ff2`, which includes the upstream security fix, with the **legacy** participation screen loaded through `embed.js`. R1–R3 were first run on `30367002` and rerun on `d3d38cec` on 2026-10-13 with the same results apart from the fix (addenda in each note).
- **Why:** in Chromium, Firefox and WebKit (Safari's engine), first-load voting under an xid works, and so do the "can vote" and "can write statements" switches, 32-character xids, the admission list and instant admission (R1).
- **Not chosen:** the rewritten screen (`/alpha/`). It still ignores settings we need (upstream issue #2384) and, when self-hosted, points at pol.is.
- **Note:** Pol.is has no releases, so we pin by commit. Before any upgrade, rerun the R1 test suite (`research/r1/`) against the new commit.

## 2. Host

- **Recommend (maintainer's direction, 2026-10-12; detail in decision 002):** buy a used tower server through government surplus (GovDeals). Host it at an office, or failing that a member's home. Split it with Proxmox VE so the bridge gets its own virtual machine and future NTARI projects can use the rest.
- **How it's reached:** the server keeps an **outbound-only** WireGuard tunnel to a small rented relay, about $5/month. The relay does TLS passthrough, so it forwards encrypted traffic it can't read. No ports open at the site; this matches the JFA substrate's no-inbound-ports design.
- **Sizing:** R1 measured the core Pol.is stack at about 240 MB of memory, so most of the machine is free for later projects. The opinion-map calculator was not measured; its default memory cap of 16 GB must be lowered.
- **Tradeoffs the board accepts:**
  - used hardware with no warranty;
  - one location, so a power or internet outage closes and reruns an open round;
  - volunteers maintain the machine;
  - the site's household or office is physically near vote data while a round is open.
- **Alternative (R6's recommendation):** rent a 4 GB VPS for about $24/month. Simpler to run, but the hosting company could in principle read the server, and it accepts inbound traffic.
- **Ruled out either way:** Cloudflare Tunnel. It decrypts traffic, so Cloudflare could link members to votes.

## 3. Domain names

- **Recommend:** `polis.ntari.org` (Pol.is) and `vote.ntari.org` (the bridge's pages).
- ntari.org's DNS is on Wix's nameservers, and Wix's DNS manager can add the two A records. The main website is unaffected.
- **Why the same domain:** Safari blocks cookies from other sites inside embedded frames, so Pol.is and the bridge must share a domain.

## 4. Eligibility scope

- **Options:**
  - (a) Only members on the round's federation roll may take part.
  - (b) All members, because standing extends everywhere.
- **Recommend (a).** A round informs one federation's decision, and §6.3 has a member put a matter before *their own* federation. Option (b) would mix other federations' views into the opinion map, and results can't be split by federation in the MVP.
- **Note:** this recommendation is reasoning, not research. No spike tested it.

## 5. Roll source

- **Options:**
  - (a) A Slack user group per federation.
  - (b) Membership of the federation channel.
  - (c) A roll file.
- **Recommend (a).** The channels are public, so anyone can join one, which makes channel membership self-selected.
- NTARI's Slack is on Pro, free through Slack for Nonprofits since 2025-07-21, which includes user groups (R4).
- **Conditions:**
  - only Owners and Admins may edit user groups (an admin setting, not yet checked);
  - each member, including organization members, maps to exactly one Slack account (§3.4, one vote per member).
- **Watch:** free Pro covers 250 members or fewer.

## 6. Round key policy

- **Options:**
  - (a) Destroy each round's key at close.
  - (b) Keep a long-lived key held by the Secretary.
- **Recommend (a).** After close, nobody, including the server's operators, can link a Slack account to votes. Keys live only in memory (`tmpfs`) and never in backups, and the provider's disk snapshots stay off (R6).
- **Cost:** if the server restarts mid-round, the key is lost, and the round closes early and is rerun.
- **What (b) would mean:** re-auditing by identity becomes possible, but the key holder could de-anonymize every vote.

## 7. Where round records go

- **Recommend (R5, D1):** a **proceedings log**. That's one JSON line per closed round, appended through a PR to a registry repo that the Secretary's office approves.
- **What a record holds:** only hashes, types, timestamps and references, with no names or counts. Records are chained, so any edit is detectable, and corrections are new records that point at the old one. The full example is in `docs/research/R5-ntari-constraints.md` §5.1.
- **Why not Tell yet:** Tell's v0.1.0 release contains no code and has no way to append a record.
- **Why not the §9.5 governance registry:** §9.5's list of registry contents doesn't include deliberation rounds. The registry cites a round only when a binding decision relies on it.
- **Needs:** a repo name and the Secretary's sign-off on the merge path.

## 8. Who may convene

- **Options:**
  - (a) Any member, in their own federation's channel.
  - (b) Named officers on request (v1.1 §8.3, §8.6).
- **Recommend (a).** §6.3 lets any member raise a matter, and §7.6 bars the Board from adding approval steps.
- **Enforcement:** the bridge checks the convener is on that federation's roll (§5), so no separate convener list is needed.

## 9. Shared-browser protection

- **The problem (R1, verified in all three engines):** if two members use the same browser for the same round, Pol.is files the second member's votes under the first. This even works for someone never admitted, and the audit can't see it.
- **Recommend (R2, verified in Chromium and WebKit):** NTARI's proxy serves a small reset page on the Pol.is address, loaded before every vote page. It clears the previous member's Pol.is session, so each member gets their own. The join page also tells members to use their own device. No change to Pol.is is needed.
- **Also:** raise an upstream issue asking Pol.is to treat a different xid as a different person.
- **Not covered:** a browser that is *signed in* to a Pol.is account votes as that account. The audit catches this, and operators must never sign in on a voting browser.

## 10. Pol.is accounts and admission

- **Recommend (R2, R3):**
  - **One Pol.is owner account,** relying on the per-round xids. Admitting a member who was already admitted elsewhere under the same owner can silently do nothing, so the bridge must check that each admission really took effect.
  - **Admit members through the Pol.is API** using an operator login from an identity provider the bridge controls. Pol.is admin login is OIDC-only.
  - **Read results at close** through a read-only database role (`bridge_audit`, tested).
  - **Close self-registration** at the identity provider. Pol.is has no sign-up switch of its own, and a signed-in account bypasses the admission list.
- **Accept:** admission cannot be revoked once someone has voted. The real control is the end-of-round audit, run against the bridge's own admitted set (R3's audit SQL is written and tested).
- **Needs:** who holds the operator accounts (Gate 2).

## 11. When results become visible

- **Recommend (R3):** Pol.is's report and its downloads need no login, so the report is created only **at close**, then published with the hash.
- During the round, the conversation and report identifiers are treated as secrets.

## 12. What round summaries show

- **Recommend (R5, D4):** the summary shows counts, the report link and the hash, but no "consensus" or score.
- **Why:** §6.9 says one documented harm reopens a result and harm is never averaged away, and no policy yet says how that applies to a Pol.is round.
- **For Gate 4:** the P1-005 amendment must say how a documented harm raised in a round reopens the result.
- **Also decide (D8):** should a minimum number of participants be required before counts are posted? With tiny rolls, counts can reveal who took part.

## 14. Operating details (R6, decision 002)

Decide or delegate each item:

1. **Budget:** about $450–1,450 one-time for the server, drives and UPS, plus about $180–205/year for the relay and electricity (decision 002). Who approves it?
2. **Site:** office or home, and who hosts? Custody agreement and asset-register entry (decision 002).
3. **Access:** who are the two admins holding the server and relay logins?
4. **Backups:** which off-site storage, and who holds the backup decryption key? It must be separate from round keys, which are never backed up.
5. **DNS:** who has Wix access to add the two records?
6. **Reboots:** freeze automatic updates and reboots while a round is open.
7. **NTARIHQ facts:** PLAN.md calls NTARIHQ an Ubuntu server, but internal notes describe Windows. Correct the record either way.

## 15. Preconditions for any round (not up for decision)

These come from verified findings. Phase 2 builds them, and Phase 4 checks them:

1. **The proxy blocks** `/api/v3/xid/`, `/api/v3/conversationUuid`, `/api/v3/zinvites/`, `/api/v3/convSubscriptions` and `/api/v3/notifications/`, and blocks `/api/v3/reportExport/` until close (R3). Upstream now owner-gates the UUID and invite routes, but the xid list download still needs no login and an xid still works as a password. These blocks keep it that way from outside.
2. **Logs never record xids or member IP addresses:**
   - an nginx log format without query strings, IP, Referer or user agent;
   - Pol.is `SERVER_LOG_LEVEL=error`;
   - rotation for Docker's logs (R3).
3. **Security headers:**
   - Pol.is pages get a Content-Security-Policy that only lets `vote.ntari.org` frame them and blocks third-party scripts (the analytics tracker and an unpinned CDN script);
   - the bridge's vote page sends `Referrer-Policy: same-origin`, because other values break voting in WebKit (R2, R3).
4. **Pol.is configuration:**
   - `DEV_MODE=false`;
   - participant token keys (`JWT_PRIVATE_KEY`/`JWT_PUBLIC_KEY`) set;
   - analytics, translation and AI features off;
   - per conversation, the xid allow-list on, xid required, and email subscription off (R1, R3).
5. **After close:** purge the stored page addresses that contain xids (`participants_extended`) once the bundle is hashed and the audit has passed (R3).
6. **Slack logging:** Bolt runs at INFO or above, never DEBUG, which logs whole payloads including Slack user IDs. A test enforces this (R4).
